RAG 与 Agent：让 LLM 连接外部世界

RAG 解决“模型不知道最新/私有知识”；Agent 解决“模型不能只回答，还要观察环境、调用工具、循环完成任务”。两者本质都在把参数内知识扩展成外部可获取状态与能力。

2. Chunking：为什么文档不能整篇直接做一个向量

Chunk 粒度决定召回和上下文质量。

Chunk 太小

  • 语义被切碎
  • 上下文缺失
  • 召回到一句话但不知道章节背景

Chunk 太大

  • 一个向量混太多主题
  • 检索精度下降
  • Prompt token 成本上升
固定 tokenOverlap按标题/段落Semantic ChunkParent-Child Retrieval

3. Dense Retrieval 为什么还要配 BM25

语义相似和关键词精确匹配是互补的。

Dense / Embedding

擅长“表达不同但语义相近”。

BM25

擅长 ID、产品名、错误码、专业术语等精确词。

Hybrid Search

两路召回后做融合，再交给 Reranker。

企业 RAG 中“只上向量库”往往不够，尤其是日志、代码、产品编号和法律条款场景。

4. Retriever 与 Reranker 分工不同

第一阶段追求 Recall，第二阶段追求精确排序。

100 万文档太多，不能全精排
Retriever快速找 50 个
Reranker精排成 Top 5
LLM Context只放高质量证据

5. RAG 错了，先别怪 LLM

完整链路每层都能出错。

Query表达有歧义？
Rewrite改坏了吗？
Retrieve召回了吗？
Rerank排对了吗？
Context被截断了吗？
LLM是否忠于证据？

Retrieval Eval

Recall@K、Precision@K、MRR、nDCG。

Generation Eval

Correctness、Faithfulness、Citation Correctness、Completeness。

6. Tool Calling：模型只负责“提出调用”，Host 才真正执行

这点是 Agent 工程边界的核心。

User“查东京天气”
LLMtool_call(get_weather)
Host校验参数/权限
Tool真正执行 HTTP/API
LLM读 tool_result 再回答
LLM 本身通常没有“魔法访问数据库”的能力。真正的文件、HTTP、数据库操作由 Host / Tool Runtime 执行。

8. Memory、State、Context 别混在一起

“存到数据库”不代表模型就自动记住了。

概念是什么模型当前能直接看到？
Context本次模型调用真正输入的 tokens能
Session State任务运行时结构化状态，如 runId、tool results、budget只有注入 Context 才能
Long-term Memory数据库/向量库中的跨会话信息必须检索/加载回来

9. MCP：统一的是“怎么接工具”，不是“模型突然获得所有权限”

它把 Host 与 Tool/Resource Server 的接口标准化。

Agent / Host发现工具
MCP Protocol统一调用格式
MCP Server封装真实服务
Git / DB / Files真正能力来源
认证、权限、Secret、Sandbox 仍然必须由系统设计解决，协议本身不会自动消除安全问题。

10. Prompt Injection：RAG / Agent 为什么比纯聊天更危险

外部文档本身可能包含恶意指令。

Instruction/Data 分层

检索到的文本只能作为数据，不能升级成系统指令。

Least Privilege

Tool 只给完成任务所需最小权限。

Policy Engine

真正权限边界用代码强制，而不是只靠 System Prompt。

Human Approval

转账、删除、发布等高风险动作需要人工确认。
