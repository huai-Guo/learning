2. Prefill 与 Decode：同一个模型，两种完全不同的性能阶段

这是部署面试最重要的一组概念。

Prefill

  • 一次处理整个 Prompt
  • token 间可并行
  • 大矩阵乘法占比高
  • 通常更偏 Compute-bound
  • 建立初始 KV Cache

Decode

  • 每步新增一个 token
  • 严格串行依赖前一步
  • 反复读取历史 KV
  • 容易 Memory-bandwidth-bound
  • 决定 TPOT
为什么会有 PD 分离？ 因为 Prefill 和 Decode 的硬件瓶颈不同，可以独立调度甚至放到不同 Worker。

3. KV Cache：到底缓存了什么，又没缓存什么

它避免的是“历史 K/V 投影重复计算”，不是让模型不再看历史。

没有 KV Cache
Step 1算 token1 K/V
Step 2又算 token1 + token2
Step 3又算 token1..3
有 KV Cache
历史 K/V直接复用
New Token只新算 Q/K/V
AttentionQ_new 仍要看历史 K
高频误区：KV Cache 不会把 Attention 变成“只看新 token”；它只是避免历史 token 的 K/V 投影反复重算。

4. 为什么 GQA 会直接影响并发能力

KV Cache 的大小与 num_kv_heads 线性相关。

KV bytes ≈ 2 × layers × seq_len × num_kv_heads × head_dim × bytes × batch

MHA

KV heads 多，缓存大。

GQA

多个 Q heads 共享 KV，缓存明显下降。

MQA

所有 Q 共享一套 KV，最省。

同样显存下，KV 更省通常意味着：能放更长上下文、更多并发请求或更大 batch。

5. Logits 之后，模型怎么选下一个 token

生成不是只有“取最大值”。

Greedy

每步 argmax。稳定、确定，但缺少多样性。

Temperature

控制分布尖锐程度。低温更确定，高温更多样。

Top-k

只保留概率最高的 k 个 token。

Top-p

保留累计概率达到 p 的最小候选集合，更自适应。

代码 / JSON / 数学通常偏低随机性；创意写作可以更开放。真正参数应该用自己的 Eval 集调，而不是照抄网络模板。

6. Prefix Cache：公司 5000 token System Prompt 为什么不用每次重算

跨请求复用相同前缀的 KV。

公共 System Prompt公司规则 / Tool Schema
首次 Prefill生成 Prefix KV
Cache按前缀 Hash 保存
后续请求直接复用，再算用户增量
多租户场景要考虑 Cache Isolation、权限、隐私和 Timing Side Channel，不能只看性能。

7. PagedAttention：为什么 KV Cache 要像操作系统内存一样“分页”

请求长度不同，如果都预留最大连续空间，会浪费很多显存。

连续预留

Request A 只用了 2K，却预留 32K；Request B 只用了 8K，也预留 32K。内部碎片明显。

分页管理

KV 被切成固定 block，需要多少就分多少，通过 block table 映射逻辑序列。

价值：降低碎片、提高 KV 利用率、支持动态请求长度和更高并发。这是 vLLM 早期最具代表性的设计之一。

8. Continuous Batching：为什么 Batch 不是固定的一组请求

在线请求随时来、输出长度也完全不同。

Static Batch

  • A 要 100 token
  • B 只要 20 token
  • B 结束后槽位可能闲着

Continuous Batch

  • B 完成立即移出
  • 新请求 C 立即加入
  • GPU batch 持续保持饱和

9. TTFT、TPOT、Throughput：不要只说“延迟”

不同指标对应不同用户体验和瓶颈。

TTFT

请求进入到第一个 token。受排队、Prefill、调度影响大。

TPOT

首 token 之后每个输出 token 的平均时间。Decode 性能关键。

Throughput

单位时间处理的 token/request 数。通常和单请求 latency 有权衡。

线上要看 P50/P95/P99，而不是只报一个平均值。
