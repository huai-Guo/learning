Chapter 06 · Modern Protocols

HTTP/2、HTTP/3、QUIC、WebSocket、RPC：
现代协议到底在解决什么问题？

不要把协议背成一张名单。正确主线是：HTTP/1.1 并发能力有限 → HTTP/2 用 Frame + Stream 多路复用 → TCP 仍有全局有序阻塞 → QUIC 重做现代传输 → HTTP/3 建在 QUIC 上。WebSocket 与 RPC 则分别解决“长期双向消息”和“远程方法调用”。

HTTP 演进

  • HTTP/1.1：Persistent Connection，但并发模型受限。
  • HTTP/2：Binary Framing、Stream、Multiplexing、HPACK。
  • HTTP/3：HTTP Semantics over QUIC。

不要混层

  • WebSocket 是应用层双向消息协议。
  • RPC 是调用模型/框架。
  • TCP / QUIC 才是它们下面的传输能力。

HTTP/2

1. 为什么要引入 Binary Frame、Stream 与 Multiplexing？

HTTP/1.1 的历史痛点
多个资源 ↓ 常开多条 TCP Connections ↓ 更多握手 更多 Socket 多套拥塞控制状态 重复 Header

HTTP pipelining 虽存在，但没有成为浏览器主流并发方案。

HTTP/2 的答案
One TCP Connection ├─ Stream 1 │ ├─ HEADERS │ └─ DATA ├─ Stream 3 └─ Stream 5

不同 Stream 的 Frame 可以交错发送，由 Stream ID 重新归类。

Connection

一条 HTTP/2 底层连接。

Stream

Connection 内独立的逻辑双向流。

Message

一个 Request 或 Response。

Frame

HTTP/2 在线上传输的协议单位。

HPACK

通过静态表、动态表与 Huffman Coding 压缩重复 Header。

Flow Control

HTTP/2 自己也有 Stream / Connection 级流量控制，不等于 TCP rwnd。

瓶颈下沉到 TCP

2. HTTP/2 已经多路复用，为什么仍然会有 TCP-level HOL？

HTTP/2 Layer

Stream 1 慢，不要求 HTTP 层停止 Stream 3 / 5 的 Frame。

TCP Layer

多个 HTTP/2 Streams 最终仍进入同一条 TCP Byte Stream，而 TCP 必须有序交付。

TCP bytes 1...1000 ✓ TCP bytes 1001...2000 ✗ lost TCP bytes 2001...3000 ✓ arrived 低序号缺口没有恢复 ↓ 后续 bytes 暂时不能交给 HTTP/2 parser ↓ 多个 HTTP/2 Streams 一起受影响
!
HTTP/2 解决了很多 HTTP 层 HOL，但没有消灭 TCP HOL
理解这一点，才能自然理解 QUIC 为什么要把独立 Stream 下沉到传输层。
QUIC

3. QUIC 为什么选择 UDP 作为底层接口？

不是为了“不可靠”

UDP 只提供最小 Datagram 接口；可靠性由 QUIC 自己实现。

部署与迭代

QUIC 常在用户态实现，不必等待 Kernel TCP 全面升级才能部署新恢复/拥塞算法。

独立 Streams

传输层原生提供多 Stream，避免所有逻辑流都被压进一条全局有序 Byte Stream。

HTTP/3 ↓ QUIC ↓ UDP ↓ IP QUIC 自己负责： Reliability / ACK Loss Recovery Streams Flow Control Congestion Control TLS 1.3 Integration Connection ID
QUIC 也要做“难活”

4. ACK、Loss Recovery、Flow Control、Congestion Control

ACK / RTT

QUIC Packet Number 用于确认、RTT Estimation 与 Loss Detection。

Loss Recovery

丢失的是 Packet，但可靠信息可以在新的 Packet Number 中重新发送。

Flow Control

既有 Stream-level，也有 Connection-level，限制 Receiver 能接收的数据量。

Congestion Control

根据 ACK、RTT、Loss、ECN 等网络信号控制发送速率与在途数据。

i
“UDP 没有拥塞控制”不等于“QUIC 没有拥塞控制”
UDP 本身不提供；QUIC 作为上层传输协议必须自己承担这些职责。
QUIC 数据模型

5. Packet Number、Stream Offset、Connection ID 各自解决什么？

Packet Number

Packet-level ACK、Loss Detection、RTT；重传信息使用新的 Packet Number。

Stream ID + Offset

标识是哪条 Stream、以及该 Stream 内的数据位置，用于独立重组与顺序交付。

Connection ID

让 Connection Identity 不完全绑定当前 IP:Port，为网络迁移提供基础。

QUIC Connection ├─ Stream 1 │ └─ offset 1000~1499 lost → 只等自己恢复 ├─ Stream 3 │ └─ complete → 继续交给 HTTP/3 └─ Stream 5 └─ complete → 继续交给 HTTP/3
Connection Migration
5G → Wi-Fi ↓ src IP / port changes ↓ CID identifies existing connection ↓ Path Validation ↓ update path / congestion state ↓ continue
不要过度简化

CID 不替代 IP/UDP 寻址；新路径还必须经过 Path Validation。并且同一 QUIC Stream 内仍然有自己的顺序要求。

HTTP/3

6. HTTP/3：不是“HTTP/2 + UDP”

HTTP/1.1
HTTP/1.1 ↓ TLS ↓ TCP ↓ IP
HTTP/2
HTTP/2 ↓ TLS ↓ TCP ↓ IP
HTTP/3
HTTP/3 ↓ QUIC + TLS 1.3 integration ↓ UDP ↓ IP
QPACK

Header Compression 需要适配 QUIC 多 Stream 独立推进，避免压缩状态本身重新制造大范围阻塞。

Control / QPACK Streams

HTTP/3 除 Request Streams 外，还有 Control Stream、QPACK Encoder / Decoder Streams 等单向流。

i
HTTP/2 Server Push 不应再作为今天的核心卖点
协议曾定义 Server Push，但现代 Browser 实践已经明显弱化/移除该能力。理解 HTTP/2 应把重点放在 Frame、Stream、Multiplexing、HPACK 与 Flow Control。
双向消息

7. WebSocket：解决长期 Full-Duplex 通信，不是“HTTP 太慢”

Polling

Client 周期性问“有新消息吗？”，简单但有大量空请求。

Long Polling

Server 暂时挂起 Request，有事件或超时再 Response，然后 Client 再开下一轮。

WebSocket

建立长期双向 Message Channel，双方都可以主动发消息。

经典 HTTP/1.1： GET /chat HTTP/1.1 Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: ... ↓ HTTP/1.1 101 Switching Protocols ↓ WebSocket Frames / Messages
TCP Keepalive

Kernel TCP 层确认长期空闲连接是否仍可达。

WebSocket Ping/Pong

WebSocket Protocol 层确认 Peer 是否响应。

Business Heartbeat

业务层确认 Session / Room / Game State 是否健康。

i
WebSocket 不只存在于 HTTP/1.1 Upgrade
现代标准也支持基于 HTTP/2 / HTTP/3 的 Extended CONNECT 方式建立 WebSocket。
远程调用抽象

8. RPC：不是一种固定网络协议

userService.getUser(42)
↓
Client Stub / IDL
↓
Serialization
↓
RPC Protocol / Metadata / Deadline
↓
HTTP/2 / TCP / QUIC / Other Transport
↓
Server Stub → Business Method
gRPC
Application Method ↓ gRPC ↓ Protocol Buffers ↓ HTTP/2 ↓ TLS ↓ TCP

gRPC 不等于 HTTP/2；HTTP/2 是它常用的底层协议。

Thrift
Thrift IDL ↓ Generated Code ↓ Protocol Binary / Compact ↓ Transport

Thrift 是一整套 RPC 工具链，不能把“Thrift vs TCP”当成同层比较。

RPC 调用形态

9. Unary、Streaming，以及 REST vs RPC

Unary

一个 Request 对一个 Response。

Server Streaming

一个 Request，Server 连续返回多个 Message。

Client Streaming

Client 连续发送多个 Message，Server 最后返回一个结果。

Bidirectional

双方都维护独立 Message Stream，可并行发送。

REST-style
Resource URI HTTP Method Representation Status Code GET /users/42
RPC-style
Service Method Arguments Return Value UserService.GetUser(42)
!
REST = HTTP，RPC = TCP 是错误的
RPC 可以建立在 HTTP/2、TCP、QUIC、WebSocket 等不同传输上；HTTP JSON API 也可以设计成明显的 RPC 风格。
工程可靠性

10. Deadline、Cancellation、Retry、Idempotency：RPC 真正难的地方

Deadline

传播整个调用链剩余预算，避免下游无限等待。

Cancellation

上游不再需要结果时，尽量停止下游无意义工作。

Retry

Timeout 不等于远端没执行。盲目重试可能重复业务动作。

Idempotency

结合 Request ID、Idempotency Key、Deduplication 等降低重复执行风险。

Client ↓ charge once Server ↓ business succeeded Response ✗ lost Client only sees: Timeout 无法仅凭网络现象判断： A. Server 没执行 B. Server 已执行，但 Response 丢了
服务寻址

11. Service Discovery 与 Load Balancing：Name → Endpoint Set → Pick One

DNS-based
user-service.internal ↓ DNS / CoreDNS 10.23.4.12 10.23.4.19 10.23.5.31

简单通用，但需要考虑 TTL、Cache、健康粒度与变更实时性。

Registry-based
Service Instance ↓ register / lease Service Registry ↓ endpoint / health / metadata Client / Proxy / LB

更显式地维护实例、租约、健康和元数据。

Client-side LB

Client 拿到 Endpoint Set 后自己挑目标。

Server-side LB

Client 只连稳定入口，由 Proxy / LB 再选择后端。

12. 一页总结：这些技术不是互相替代，而是在不同层解决不同问题

HTTP/1.1 ↓ 并发 / framing 限制 HTTP/2 ↓ Frame + Stream + Multiplexing TCP ↓ global ordered byte stream TCP HOL ↓ QUIC ↓ independent streams + recovery + congestion + TLS 1.3 HTTP/3 旁支： WebSocket → 长期双向 Message Channel RPC → Remote Method Call abstraction → gRPC / Thrift / custom RPC → Deadline / Retry / Discovery / LB
