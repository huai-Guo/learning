Chapter 06 · Modern Protocols

HTTP/2、HTTP/3、QUIC、WebSocket、RPC：
现代协议到底在解决什么问题？

不要把这些协议背成一张名单。正确的学习方式是沿着因果链：HTTP/1.1 并发不够 → HTTP/2 用 Frame + Stream 多路复用 → 底层 TCP 仍有全局有序阻塞 → QUIC 重做传输能力 → HTTP/3 建在 QUIC 上。WebSocket 和 RPC 则属于另外两类需求。

版本演进主线

  • HTTP/1.1：Persistent Connection，但并发能力有限。
  • HTTP/2：Binary Frame、Stream、Multiplexing、HPACK。
  • HTTP/3：HTTP Semantics over QUIC。

两条旁支

  • WebSocket：长期双向消息通道。
  • RPC：把远程通信包装成方法调用。

HTTP/2

1. HTTP/2 为什么要引入 Binary Frame 与 Stream？

HTTP/1.1 的痛点
多个资源 ↓ 常需要多条 TCP connections ↓ 更多握手 更多 Socket 多套拥塞控制 Header 重复

HTTP pipelining 长期没有成为浏览器主流并发方案。

HTTP/2 的答案
One TCP Connection │ ├─ Stream 1 │ ├─ HEADERS │ └─ DATA │ ├─ Stream 3 │ ├─ HEADERS │ └─ DATA │ └─ Stream 5

不同 Stream 的 Frame 可以交错，接收端根据 Stream ID 重新归类。

Connection

一条 HTTP/2 底层连接。

Stream

Connection 内的逻辑双向流。

Message

一个 HTTP Request 或 Response。

Frame

HTTP/2 在线上传输的协议单位。

i
HPACK 为什么存在？
Header 很容易重复。HPACK 用 Static Table、Dynamic Table 与 Huffman Coding 减少重复传输，但这也引入了双方压缩状态同步。
真正的瓶颈下沉到 TCP

2. HTTP/2 已经多路复用，为什么还会有 TCP-level HOL？

HTTP/2 Layer

Stream 1 慢，不代表 HTTP 层必须暂停 Stream 3 / 5 的 Frame。应用层并发已经显著改善。

TCP Layer

多个 Stream 最终仍被编码进同一条 TCP Byte Stream，而 TCP 必须有序交付。

TCP bytes 1...1000 ✓ TCP bytes 1001...2000 X lost TCP bytes 2001...3000 ✓ arrived TCP 必须等待中间缺口 ↓ 后续字节暂时不能交给 HTTP/2 parser ↓ 不同 HTTP/2 Streams 也可能一起被拖住
!
所以“HTTP/2 解决了 HOL”只说对了一半
它解决了很多 HTTP 层串行限制，但没有消灭 TCP 自己的全局有序 Byte Stream 阻塞。
QUIC

3. QUIC 为什么选择 UDP 作为底层接口？

不是为了“不可靠”

UDP 只提供最小 Datagram 接口，QUIC 自己重新实现可靠性。

更容易部署

QUIC 常在用户态实现，新算法不必等待 OS Kernel TCP 全面升级。

重做 Stream 模型

每条 Stream 独立维护有序性，避免一条全局 Byte Stream 把所有逻辑流绑在一起。

HTTP/3 ↓ QUIC ↓ UDP ↓ IP QUIC 自己负责： ACK Loss Recovery Reliable Streams Flow Control Congestion Control TLS 1.3 Integration Connection ID
i
用户态实现 ≠ 普通应用协议
从职责上，QUIC 承担了大量传统 Transport Protocol 的工作，只是其实现位置通常比 TCP 更靠近应用进程。
QUIC 数据模型

4. Packet Number、Stream Offset、Connection ID 分别解决什么？

Packet Number

用于 ACK、Loss Detection、RTT 等 Packet-level recovery。重发相关可靠信息时使用新的 Packet Number。

Stream ID + Offset

描述某条 Stream 的数据位置，负责 Stream-level reassembly 与有序交付。

Connection ID

让 QUIC Connection Identity 不完全依赖 IP:Port 四元组，为网络迁移提供基础。

QUIC Connection ├─ Stream 1 │ └─ offset 1000~1499 lost → 等自己恢复 ├─ Stream 3 │ └─ data complete → 继续交给 HTTP/3 └─ Stream 5 └─ data complete → 继续交给 HTTP/3
!
QUIC 不是“完全没有 HOL”
同一个 Stream 内仍然有自己的顺序要求。它解决的是“一条 Stream 的丢包不会因为全局有序 Byte Stream 而阻塞其他独立 Stream”。
Connection Migration
5G → Wi-Fi ↓ src IP / port changes ↓ CID still identifies connection ↓ Path Validation ↓ update path / congestion state ↓ continue
不要过度简化

Connection ID 不替代 IP/UDP 寻址；新路径仍需 Path Validation，避免地址欺骗与放大攻击。

HTTP/3

5. HTTP/3：不是“HTTP/2 + UDP”，而是 HTTP Semantics over QUIC

HTTP/1.1
HTTP/1.1 ↓ TLS ↓ TCP ↓ IP
HTTP/2
HTTP/2 ↓ TLS ↓ TCP ↓ IP
HTTP/3
HTTP/3 ↓ QUIC + TLS 1.3 integration ↓ UDP ↓ IP
QPACK

为 QUIC 多 Stream 独立交付设计 Header Compression，避免直接照搬 HPACK 时重新制造压缩状态阻塞。

TLS 1.3 Integration

QUIC Transport Handshake 与 TLS 1.3 协同进行，不是简单把“TCP 上的 TLS Record”原样套在 UDP 之上。

i
HTTP/3 也不等于“永远 0-RTT”
新连接通常仍需要约 1 RTT；已有恢复状态时才可能使用 0-RTT Early Data，而且同样有 Replay Risk。
双向消息

6. WebSocket：解决的是长期 Full-Duplex 通信，不是“HTTP 太慢”

Polling

客户端反复问“有新消息吗？”，简单但产生很多空请求。

Long Polling

Server 暂时挂住 Request，有事件或超时后再返回，然后 Client 继续下一轮。

WebSocket

建立长期双向 Message Channel，Client 与 Server 都可以主动发送消息。

经典 HTTP/1.1 Upgrade： Client: GET /chat HTTP/1.1 Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: ... Server: HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade 之后： WebSocket Frames / Messages
TCP Keepalive

Kernel TCP 层探测连接可达性。

WebSocket Ping/Pong

WebSocket Protocol 层确认 Peer 还在正常处理协议。

Business Heartbeat

业务层确认 Session、Room、Game State 等是否健康。

远程调用抽象

7. RPC：不是一种固定网络协议，而是一种“远程方法调用”模型

userService.getUser(42)
↓
Client Stub / IDL
↓
Serialization
↓
RPC Protocol / Metadata / Deadline
↓
HTTP/2 / TCP / QUIC / Other Transport
↓
Server Stub → Business Method
gRPC
Application Method ↓ gRPC ↓ Protocol Buffers ↓ HTTP/2 ↓ TLS ↓ TCP

gRPC 不等于 HTTP/2；HTTP/2 只是它常用的底层传输协议之一。

Thrift
Thrift IDL ↓ Generated Code ↓ Protocol Binary / Compact ↓ Transport

Thrift 是 IDL + Codegen + Protocol + Transport 的 RPC 工具链，不应和 TCP 当成同层方案比较。

!
REST = HTTP，RPC = TCP 是错误的
RPC 可以跑在 HTTP/2、TCP、QUIC、WebSocket 等不同通道上；HTTP JSON API 也可能设计得很 RPC 风格。
工程可靠性

8. Deadline / Cancellation / Retry：RPC 真正难的不是“把请求发过去”

Deadline

传播整个调用链剩余时间预算，避免下游无限等待。

Cancellation

上游已经不需要结果时，尽量让下游停止无意义工作并释放资源。

Retry

Timeout 不代表远端没执行。重试必须和幂等、去重、Request ID 一起设计。

Client ↓ request: charge once Server ↓ already succeeded Response X lost Client sees: Timeout 问题： Server 没执行？ 还是执行成功但 Response 丢了？ 盲目 Retry → 可能重复扣款
服务寻址

9. Service Discovery 与 Load Balancing：Name → Endpoint Set → Pick One

DNS-based
user-service.internal ↓ DNS / CoreDNS 10.23.4.12 10.23.4.19 10.23.5.31

通用、简单，但要考虑 TTL、Cache、健康状态粒度与变更实时性。

Registry-based
Service Instance ↓ register / lease Service Registry ↓ endpoint / health / metadata Client / Proxy / LB

Consul / etcd 类系统更像显式维护 Endpoint 与健康/租约状态。

Client-side LB

Client 自己拿到 Endpoint Set，并自己选择本次请求的目标实例。

Server-side LB

Client 只连接稳定 VIP / Proxy，由中间入口替它完成实例选择。

10. 一页总结：现代协议并不是互相替代，而是解决不同层的问题

HTTP/1.1 ↓ 并发与 framing 限制 HTTP/2 ↓ Frame + Stream + Multiplexing TCP ↓ global ordered byte stream TCP HOL ↓ QUIC ↓ independent streams + recovery + congestion + TLS 1.3 HTTP/3 旁支： WebSocket → 长期双向 Message Channel RPC → Remote Method Call abstraction → gRPC / Thrift / custom RPC → Deadline / Retry / Discovery / LB

这一章最该记住

  1. HTTP/2 Multiplexing 不等于多条 TCP。
  2. TCP HOL 来自全局有序 Byte Stream。
  3. QUIC 在 UDP 上自己实现可靠性与拥塞控制。
  4. Packet Number、Stream Offset、Connection ID 解决不同问题。
  5. WebSocket 是消息通道；RPC 是调用模型。
