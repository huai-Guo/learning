Phase 6

HTTP/2、HTTP/3、QUIC、WebSocket、RPC

这章不是“协议大杂烩”，而是一条演化链：HTTP/1.1 的并发问题 → HTTP/2 Stream 多路复用 → TCP 层 HOL → QUIC 独立 Stream → HTTP/3；再把 WebSocket 和 RPC 放到正确层级。

总原则：HTTP/2、HTTP/3 是 HTTP 演进；WebSocket 是双向消息协议；RPC 是远程调用编程模型。它们不在同一层，不能机械横向比较。

2 · HTTP/2 的 Connection / Stream / Message / Frame

HTTP/2 Connection ├─ Stream 1 │ ├─ Request Message │ │ └─ HEADERS / DATA Frames │ └─ Response Message │ └─ HEADERS / DATA Frames ├─ Stream 3 └─ Stream 5 不同 Stream 的 Frame 可以交错发送； Stream ID 让接收端重新归类。

3 · Multiplexing 为什么还会被 TCP 拖住？

HTTP/2 Layer

Stream 可以并发

Stream 1 慢，不要求 HTTP 层停止发送 Stream 3/5 的 Frame。

TCP Layer

仍是一条全局有序 Byte Stream

低序号 TCP 数据缺失时，后面已经到达的字节也不能及时交给 HTTP/2 Parser。

4 · QUIC 为什么选 UDP？

不是为了“不可靠”

UDP 只提供最小 Datagram 接口；可靠性由 QUIC 自己实现。

更容易部署新传输逻辑

QUIC 常在用户态迭代，不必等待内核 TCP 全面升级。

重做 Stream 模型

不同 Stream 独立可靠交付，不再共享一条全局有序 Byte Stream。

5 · Packet Number 与 Stream Offset

概念解决什么
Packet NumberQUIC Packet 的 ACK、Loss Detection、RTT 等；重传相关信息会进入新的 Packet Number。
Stream ID区分是哪一条逻辑 Stream。
Stream Offset描述该 Stream 内数据的字节位置，用于重组与有序交付。

6 · QUIC 避免跨 Stream HOL

QUIC Connection ├─ Stream 1: offset 1000~1499 丢失 → 等自己恢复 ├─ Stream 3: 数据完整 → 继续交给 HTTP/3 └─ Stream 5: 数据完整 → 继续交给 HTTP/3 注意： 同一个 Stream 内仍有自己的顺序要求。

7 · QUIC 仍然要做“TCP 那些难活”

Reliability

ACK、Loss Detection、Reliable Frames。

Flow Control

Stream-level + Connection-level。

Congestion Control

根据 ACK、RTT、Loss、ECN 调整发送。

Security

把 TLS 1.3 Handshake 集成进 QUIC。

9 · HTTP/3 栈

HTTP/1.1

HTTP → TLS → TCP → IP

文本协议 framing + TCP。

HTTP/2

HTTP/2 → TLS → TCP → IP

Frame/Stream 多路复用，但仍有 TCP HOL。

HTTP/3

HTTP/3 → QUIC → UDP → IP

直接使用 QUIC Streams，Header Compression 使用 QPACK。

10 · WebSocket 是什么？

Polling

客户端不断问“有新消息吗？”

Long Polling

一次 HTTP Request 挂起较久，有事件再 Response，然后继续下一轮。

WebSocket

建立长期 Full-Duplex Message Channel，双方可主动发送消息。

11 · 经典 WebSocket Upgrade

Client: GET /chat HTTP/1.1 Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: ... Server: HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: ... 之后： WebSocket Frames / Messages 而不是普通 HTTP Request / Response。

14 · gRPC 与 Thrift 应该放在哪一层？

gRPC

RPC Framework

常见组合：gRPC + Protobuf + HTTP/2 + TLS + TCP。gRPC 不等于 HTTP/2。

Thrift

IDL + Codegen + Protocol + Transport

是一整套 RPC 工具链，不只是一个序列化格式，也不能和 TCP 当成同层方案比较。

15 · RPC 真正难的不是“发过去”

Deadline / Cancellation

限制调用链总预算，避免慢依赖无限拖住上游。

Retry

Timeout 不代表 Server 没执行；重试必须结合幂等与去重。

Discovery / LB

Service Name → Endpoint Set，再决定本次 Request 发给哪个实例。

16 · Service Discovery

DNS-based

user-service.internal → A/AAAA/SRV/Service 相关记录；Kubernetes 常配合 CoreDNS。

Registry-based

实例注册/租约/健康/metadata，由 Client、Proxy 或 LB 获取 Endpoint Set。
