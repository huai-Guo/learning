TCP / UDP · 可靠传输与状态机

这一章不只背“三次握手、四次挥手”。它从 Socket、四元组、Seq/Ack、重传、流量控制、拥塞控制一路讲到 TIME_WAIT、CLOSE_WAIT、Keepalive、RST 和真实故障场景。

一句话：TCP 用状态、序列号、ACK、重传、rwnd 和 cwnd，把不可靠 IP 上的 Segment 组织成应用可用的有序字节流；UDP 则提供轻量 Datagram，把更复杂的可靠性留给上层。

3 · 三次握手真正建立什么？

交换 ISN

双方建立自己的序列空间，后续 Seq/Ack 才有共同基准。

确认双向握手信息

Client 确认 Server SYN，Server 也确认 Client 的初始连接请求。

初始化连接状态

协商 MSS、Window Scale、SACK 等 Options，并减少旧重复连接造成混乱。

5 · Seq / Ack：TCP 不是在给“包”编号

Sequence Number

字节位置

seq=1001,len=500 表示承载 byte 1001~1500。

Acknowledgment

下一期待字节

ACK=2001 表示 2001 之前的连续字节已经确认，下一步期待 2001。

6 · TCP 是 Byte Stream，UDP 是 Datagram

TCP

没有应用消息边界

send("HELLO") + send("WORLD")，对端可能一次 recv 到 HELLOWORLD，也可能拆成多次读取。应用协议自己做 framing。

UDP

保留 Datagram 边界

应用发送两个 UDP Datagram，接收语义仍是两个 Datagram；但 UDP 本身不负责排序和重传。

7 · 丢包恢复不是只有一种方式

RTO

根据 RTT 与波动估算等待时间，超时后重传。

Fast Retransmit

经典模型借助重复 ACK 更快判断缺失数据，不必总等 RTO。

SACK

告诉 Sender 哪些后续区间已经收到，让重传更精准。

8 · rwnd 与 cwnd 不要混

Flow Control

rwnd → 保护 Receiver

接收缓冲快满时，Receiver 缩小 advertised window，避免 Sender 把接收端撑爆。

Congestion Control

cwnd → 保护 Network

Sender 根据网络拥塞信号调节在途数据，实际发送量受 min(rwnd,cwnd) 等因素约束。

9 · 四次挥手其实是“双方向分别关闭”

Active Closer Passive Closer FIN -----------------------------> <--------------------- ACK <--------------------- FIN ACK -----------------------------> Active: FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT Passive: CLOSE-WAIT → LAST-ACK → CLOSED

10 · CLOSE_WAIT 与 TIME_WAIT 看谁的问题

CLOSE_WAIT 很多

对端已经 FIN，本机应用却没有及时 close。优先检查异常路径、连接泄漏、线程卡住。

TIME_WAIT 很多

往往说明本机是主动关闭方或短连接很多。先看连接复用、连接池和创建速率，不要无脑删除状态。

13 · 三种“保活”不是一回事

TCP Keepalive

内核层探测长期空闲 TCP 连接是否仍可达。

HTTP persistent connection

应用层在同一 TCP 连接上复用多个 HTTP 请求。

Application Heartbeat

业务协议确认对端应用和会话是否真的健康，例如 WebSocket Ping/Pong。

15 · 记忆模型

连接建立：ISN + Options + State。
