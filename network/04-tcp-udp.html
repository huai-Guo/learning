Chapter 04 · Reliable Transport

TCP / UDP：
IP 只是尽力交付，TCP 为什么还能提供“可靠字节流”？

这一章不把 TCP 简化成“三次握手 + 四次挥手”。真正的主线是：连接状态、字节序号、ACK、重传、接收窗口、拥塞窗口、关闭状态共同把不可靠 IP 组织成应用可用的可靠字节流。

TCP 最核心的 6 个关键词

  • 四元组
  • 状态机
  • Seq / Ack
  • Retransmission
  • rwnd / cwnd
  • FIN / RST / TIME_WAIT

UDP 最重要的定位

  • 保留 Datagram 边界。
  • 没有 TCP 式连接、顺序与重传。
  • 上层协议可以自己重做可靠性，例如 QUIC。

3. Seq / Ack：TCP 编号的是“字节位置”，不是“第几个包”

Sequence Number
seq = 1001 len = 500 表示携带： byte 1001 ~ 1500

Packet 只是承载这些字节的容器，TCP 真正追踪的是字节空间。

Acknowledgment Number
ACK = 2001 表示： 2001 之前的连续字节已确认 下一步期待 byte 2001

TCP 的经典累计 ACK 表达“连续收到哪里”。

i
为什么 TCP 是 Byte Stream？
send("HELLO") + send("WORLD")，对端可能一次 recv 到 HELLOWORLD，也可能拆成多次读取。应用层要自己定义消息边界。

4. RTO、Fast Retransmit、SACK：TCP 怎么知道“该重发什么”？

RTO

超时重传

根据 RTT 与波动估算等待时间。迟迟收不到确认，就认为数据可能丢失并重传。

Fast Retransmit

不总等超时

经典模型中，重复 ACK 可以提示前面存在缺口，从而更快触发重传。

SACK

更精确告诉 Sender

Receiver 可以指出哪些后续区间已经收到，减少不必要的整段重传。

Sender: 1001~1500 ✓ 1501~2000 X lost 2001~2500 ✓ 2501~3000 ✓ 累计 ACK： 仍然可能只能告诉你“下一期待 1501” SACK： 还能额外告诉你 2001~3000 已经在我这里
发送速率控制

5. rwnd 与 cwnd：一个保护 Receiver，一个保护 Network

rwnd · Receive Window

Flow Control

Receiver 告诉 Sender：我还有多少接收缓冲空间。目的是避免发送方把接收端 buffer 撑爆。

cwnd · Congestion Window

Congestion Control

Sender 根据 ACK、Loss、RTT 等网络信号控制在途数据量。目的是保护网络而不是某个单独 Receiver。

大致理解： 实际在途发送能力 ≈ min(rwnd, cwnd) 再受 socket buffer、pacing、app write rate 等限制
Sliding Window

Sender 不必发一个 byte 就等一个 ACK，可以允许一批数据同时在途。

Zero Window

Receiver 没空间时可以宣布窗口为 0，Sender 需要等待并探测窗口何时恢复。

Slow Start / CA

通过逐步增加发送规模并根据拥塞信号调整，避免一开始就把网络打满。

7. RST、拔网线、SYN 丢失：连接坏掉时到底发生什么？

No Listener

访问未监听的 TCP Port 时，常见表现是收到 RST，应用看到 Connection refused。

Firewall Drop

如果 SYN 被静默丢弃，Client 往往会重传 SYN，最终表现为 timeout。

listen but no accept

握手仍可能完成，但 accept queue 会积压，最终表现取决于 backlog 和系统策略。

拔网线
ESTABLISHED ↓ Physical Link Lost ↓ 对端不会收到“网线断了”TCP Packet ↓ 后续依赖： Retransmission Failure TCP Keepalive Application Heartbeat OS Error
进程崩溃 vs 整机断电

进程退出但 OS 还活着时，OS 可能正常关闭 Socket；整机断电则没有机会优雅发 FIN，远端只能靠超时、Keepalive 或后续发送失败感知。

!
RST 是“立即终止/拒绝连接状态”的控制信号
它和 FIN 的“有序关闭”不同，也和静默丢包造成的 timeout 不同。

8. TCP 与 UDP：不是“高级版 vs 低级版”

维度TCPUDP
数据抽象Byte StreamDatagram
连接状态有无 TCP 式握手
顺序 / 重传内建UDP 本身不提供
Flow Control有无内建
Congestion Control有UDP 本身无内建
Message Boundary不保留应用消息边界保留 Datagram 边界
TCP Keepalive

Kernel TCP 层探测长期空闲连接是否仍可达。

HTTP persistent connection

HTTP 层复用底层连接，不等于 TCP Keepalive。

Application Heartbeat

业务层判断 Session / Room / Game 等状态是否真正健康。

9. 一页总结：TCP 的可靠性来自一组机制共同工作

【建立】 LISTEN ↓ SYN ↓ SYN-ACK ↓ ACK ↓ ESTABLISHED 【可靠传输】 Seq / Ack ↓ RTO / Fast Retransmit / SACK ↓ Sliding Window 【速度控制】 rwnd → 保护 Receiver cwnd → 保护 Network 【关闭】 FIN / ACK ↓ CLOSE_WAIT / FIN_WAIT ↓ TIME_WAIT 【故障】 RST Retransmission Timeout TCP Keepalive Application Heartbeat

这一章最该记住

  1. 同一个 443 可以服务大量四元组不同的连接。
  2. Seq 编号的是字节，Ack 表示下一期待字节。
  3. TCP 是 Byte Stream，不保留 send() 边界。
  4. rwnd 与 cwnd 保护对象不同。
  5. TIME_WAIT 和 CLOSE_WAIT 要根据主动/被动关闭方向理解。
