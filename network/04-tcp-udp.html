Chapter 04 · Reliable Transport

TCP / UDP：
IP 只是尽力交付，TCP 为什么还能提供“可靠字节流”？

TCP 真正的核心不是“三次握手 + 四次挥手”，而是：连接状态、字节序号、ACK、重传、流量控制、拥塞控制和关闭状态共同把不可靠 IP 组织成应用可用的可靠字节流。

TCP 的核心对象

  • LISTEN Socket 与 Connected Socket。
  • 四元组与 TCP State。
  • Send / Receive Buffer。

UDP 的定位

  • 保留 Datagram 边界。
  • 不提供 TCP 式连接、顺序和重传。
  • 上层协议可以自行实现可靠性，例如 QUIC。

连接对象

1. Port、Socket、LISTEN：同一个 443 为什么可以服务大量客户端？

Server LISTEN: 0.0.0.0:443 建立连接后： 10.0.0.10:50001 ↔ 203.0.113.20:443 10.0.0.11:50001 ↔ 203.0.113.20:443 10.0.0.10:50002 ↔ 203.0.113.20:443 TCP Connection 常用四元组识别： src IP + src port + dst IP + dst port
Port

Transport endpoint 的一部分，不等于某个进程本身。

LISTEN Socket

负责接收新连接请求，Server 可以只有一个 443 listener。

Connected Socket

握手后为具体连接维护独立状态，应用通过 accept() 获得。

Server 内核队列

2. SYN Queue 与 Accept Queue：listen() 后内核其实在帮应用排队

Client SYN ↓ LISTEN Socket ↓ 握手尚未完成的连接状态 ≈ SYN Queue / request state ↓ 三次握手完成 Accept Queue ↓ Application accept() ↓ Connected Socket
listen 但暂时不 accept

握手仍可能由 Kernel 完成并进入 Accept Queue；真正的问题是队列持续堆积、Backlog 不足或应用 accept rate 太低。

队列满了会怎样？

具体表现依赖 OS 与 TCP 配置，可能丢弃、延迟或触发重传。不要简单背成“listen 不 accept = 三次握手一定失败”。

第一次 SYN 丢失

可靠性的坐标轴

4. Seq / Ack：TCP 编号的是字节位置，不是“第几个包”

Sequence Number
seq = 1001 payload len = 500 本段覆盖： byte 1001 ~ 1500

Packet 只是承载这些字节的容器，TCP 真正追踪的是 Byte Sequence Space。

Acknowledgment Number
ACK = 2001 含义： 2001 之前的连续字节已确认 下一步期待 byte 2001

经典 ACK 是累计确认，表达“连续收到哪里”。

!
TCP 是 Byte Stream，不保留 send() 边界
两次 send() 可以被一次 recv() 读到，也可能一次发送被拆成多次读取。应用协议必须自己定义 Message Boundary。
丢包恢复

5. RTO、Fast Retransmit、SACK：TCP 如何恢复缺失字节？

RTO

超时重传

基于 RTT 与其波动估算 Retransmission Timeout；超时仍未确认则考虑重传。

Fast Retransmit

不必总等 RTO

经典算法中，重复 ACK 可以提示前面有缺口，触发更早重传。

SACK

告诉 Sender 已收到哪些区间

Receiver 能更精细地报告后续已到达的 byte ranges，减少不必要重传。

1001~1500 ✓ 1501~2000 ✗ lost 2001~2500 ✓ 2501~3000 ✓ 累计 ACK： “我还在等 1501” SACK： “2001~3000 其实已经收到了”
发送速率控制

6. rwnd 与 cwnd：一个保护 Receiver，一个保护 Network

rwnd · Receive Window

Flow Control（流量控制）

Receiver 告诉 Sender 还有多少接收缓冲空间，避免发送方把对端 Receive Buffer 撑爆。

cwnd · Congestion Window

Congestion Control（拥塞控制）

Sender 根据 ACK、Loss、RTT 等信号控制在途数据量，避免把网络路径压垮。

实际可在途发送量，大致受： min(rwnd, cwnd) 以及： socket buffer pacing application write rate 等共同限制
Sliding Window

允许多批数据同时在途，不需要每发一个 byte 就停下来等 ACK。

Zero Window

Receiver 缓冲暂时耗尽时可通告窗口为 0，Sender 暂停正常发送。

Persist / Window Probe

为避免双方因窗口更新丢失而永久等待，TCP 会使用探测机制确认窗口何时重新打开。

故障场景

8. RST、Firewall Drop、拔网线：它们为什么表现完全不同？

No Listener

访问没有监听的 TCP Port，常见响应是 RST，应用很快看到 Connection refused。

Firewall Drop

如果 SYN 被静默丢弃，没有 RST，Client 往往只能依赖重传与超时判断失败。

进程崩溃

如果 OS 仍然正常，内核可能关闭 Socket；具体是 FIN 还是 RST 与退出方式、未读数据等状态有关，不能一概而论。

拔网线 / 断网
ESTABLISHED ↓ Physical Link Lost ↓ 不会自动生成“网线断了”TCP Packet ↓ 后续依赖： Retransmission Failure TCP Keepalive Application Heartbeat OS / Link Error
整机断电

远端收不到优雅 FIN，只能在后续发送、Keepalive 或超时机制中逐渐发现对端已经消失。

10. 一页总结：TCP 的可靠性来自一组机制共同工作

【建立连接】 LISTEN ↓ SYN / SYN-ACK / ACK ↓ ESTABLISHED ↓ Accept Queue / accept() 【可靠传输】 Seq / Ack ↓ RTO / Fast Retransmit / SACK 【速度控制】 rwnd → 保护 Receiver cwnd → 保护 Network Zero Window / Persist → 处理接收端暂时无空间 【关闭与故障】 FIN / ACK → orderly close RST → immediate abort/refuse Timeout → silent loss / peer disappearance
