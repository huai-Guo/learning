Chapter 05 · Secure HTTP

HTTP / HTTPS / TLS：
浏览器到底发了什么，TLS 又如何保证“看不懂、改不了、冒充不了”？

把三个职责先分开：HTTP 定义业务语义，TLS 负责身份、机密性和完整性，TCP 负责可靠有序地搬运 TLS 字节。真正理解 HTTPS，关键不是背消息名，而是搞清“哪把钥匙干什么、谁在证明谁”。

这一章最重要的两组区分

  • ECDHE ephemeral key ≠ Certificate identity key。
  • Certificate Signature ≠ CertificateVerify ≠ Finished。

两条时间线

  • 网站部署前：CA 签发证书。
  • 用户访问时：Browser 与 Server 完成 TLS 1.3 握手。

业务语义

1. HTTP：到底怎样表达一次 Request / Response？

Request
GET /products?lang=zh-CN HTTP/1.1 Host: shop.example.com Accept: text/html Cookie: session_id=abc123 Request Line → Headers → 空行 → Optional Body
Response
HTTP/1.1 200 OK Content-Type: text/html Content-Length: 12580 Cache-Control: max-age=60 Set-Cookie: session_id=abc123 ...
Method

表达资源操作语义。GET/POST 的核心区别不是“参数放 URL 还是 Body”。

Status

2xx 成功、3xx 重定向/缓存、4xx 客户端/权限、5xx Server/Gateway 等异常。

Header

承载 Host、Content-Type、Cookie、Authorization、Cache-Control 等元数据。

i
Safe 与 Idempotent 不是同一个概念
Safe 关注“语义上是否意图修改状态”；Idempotent 关注“重复执行是否保持相同目标效果”。
同一个域名在不同协议层出现

2. DNS hostname、TLS SNI、HTTP Host / :authority 不要混

阶段字段 / 概念作用
DNShostname把 shop.example.com 解析成地址候选。
TLSSNI让共享 IP:443 的 TLS 端知道要选择哪个站点证书和配置。
HTTP/1.1Host让 HTTP Server / Reverse Proxy 选择虚拟站点或路由。
HTTP/2 / 3:authority承担 authority / host 语义。
URL: https://shop.example.com/products DNS hostname: shop.example.com TLS SNI: shop.example.com Certificate SAN: shop.example.com HTTP Host / :authority: shop.example.com
!
值相同，不代表它们是同一个字段
它们发生在不同协议阶段、解决不同问题。DNS 为寻址，SNI 为 TLS 虚拟主机选择，Host / :authority 为 HTTP 目标站点选择。
HTTP 状态与缓存

3. Cookie、Session、Cache：为什么 HTTP 可以“记住你”？

Cookie
Set-Cookie: session_id=abc123; Secure; HttpOnly; SameSite=Lax

Browser 按规则保存，并在匹配请求中自动带上。

Session
Cookie: session_id=abc123 ↓ Server Session Store ↓ user_id / cart / roles

Session 是 Server 侧会话状态模型，Cookie 只是客户端携带的标识或状态载体。

Cache
Cache-Control: max-age=60 ETag: "v42" If-None-Match: "v42" ↓ 304 Not Modified

Freshness 与条件请求让 Browser 不必每次都下载完整资源。

i
Secure / HttpOnly / SameSite 解决不同问题
Secure 控制安全传输，HttpOnly 限制普通前端 JS 读取 Cookie，SameSite 控制跨站请求携带策略。
密码学最小模型

4. Symmetric、Public-key、Hash、Signature：必须先分开

Symmetric

高效保护大量数据

例如 AES-GCM、ChaCha20-Poly1305。适合真正的 Application Data。

Public-key

Public / Private Key

用于签名、身份认证、密钥建立等场景。

Hash

单向摘要

不是 Encryption，也不存在“把 Hash 解密回来”。

Digital Signature

Private Key 签，Public Key 验

不要用“私钥加密、公钥解密”理解签名。

i
为什么 HTTPS 大量流量不用公钥直接加密？
非对称算法更昂贵。TLS 用它来做身份与密钥建立，再派生高效的对称 AEAD Traffic Keys 保护大量业务数据。
两类“公钥”

5. TLS 里最容易混的东西：ECDHE Key Share ≠ Certificate Public Key

ECDHE Ephemeral Key Share
Client ephemeral key pair + Server ephemeral key pair ↓ ECDHE ↓ Shared Secret ↓ HKDF ↓ Handshake / Application Keys

解决：这一次连接怎样安全建立 Shared Secret，并提供 Forward Secrecy。

Certificate Identity Key
Server Identity Private Key ↓ sign Handshake Transcript ↓ CertificateVerify Certificate Public Key ↓ verify

解决：当前握手方是否真的持有这个证书对应的身份 Private Key。

!
一句话
ECDHE 负责“怎么安全得到密钥”，Certificate key 负责“你到底是谁”。
证书信任

6. CA / Certificate Chain：为什么 Browser 会相信这个 Server？

时间线 A · 网站部署前
Site / Operator ↓ CSR + Domain Control CA / Intermediate CA ↓ verify Signed Server Certificate ↓ Deploy: Certificate Private Key Intermediate Chain

CA 主要发生在证书签发阶段，而不是每次用户访问时实时批准。

时间线 B · 用户访问时
Server sends: Leaf Certificate Intermediate Certificate(s) Browser has: Trusted Root CA in local Trust Store

Browser 构造并验证从 Leaf → Intermediate → Trusted Root 的认证路径。

Certificate Signature

CA 用 CA Private Key 签证书，证明它对证书里的身份和 Public Key 做了签发背书。

CertificateVerify

Server 用证书对应 Private Key 签当前 Handshake Transcript，证明当前握手方真的持有该 Private Key。

8. Session Resumption / PSK / 0-RTT：为什么第二次连接可以更快？

Resumption
Full Handshake ↓ derive resumption state / PSK ↓ Next Connection ↓ ClientHello + PSK identity / binder ↓ Server accepts ↓ shorter handshake

目标是减少网络往返和证书/签名计算成本。

0-RTT Early Data
ClientHello + Early Application Data ↓ Server processes before new handshake fully completes

优势是低延迟，风险是 Replay。像“扣款”这种不可安全重放的操作不能随便放进 0-RTT。

!
TLS 1.3 不等于“永远只有 ECDHE”
完整认证握手常见使用 (EC)DHE；恢复场景还可以使用 PSK 或 PSK+(EC)DHE。
安全边界

9. HTTPS 能保护什么，又不能保护什么？

TLS 通常保护

HTTP Method、Path、Headers、Cookie、Authorization、Body、Response Body 等业务内容。

仍可暴露 / 推断

IP、packet size、timing、TCP/UDP metadata；经典 TLS 中 SNI 也可能被观察，传统 DNS 也可能泄露 hostname。

TLS Authentication

回答：我连接的 Server 是否持有目标 hostname 对应可信证书 Private Key？

Application Authentication

回答：当前用户是谁？通常由 Cookie、Session、Bearer Token、OAuth 等解决。

HTTPS 不解决

SQL Injection、XSS、Broken Access Control、弱密码、Server 被入侵等应用安全问题。

10. 一页总结：HTTPS 真正的组合方式

HTTP → 业务语义 TLS → Certificate Chain → CertificateVerify → (EC)DHE / PSK → HKDF → Finished → AEAD Traffic Keys TCP → 可靠有序字节流 最关键： ECDHE Ephemeral Key ≠ Certificate Identity Key Certificate Signature ≠ CertificateVerify ≠ Finished CA 签发时间线 ≠ 用户运行时 TLS 握手时间线

这一章最该记住

  1. HTTP 定义业务语义，TLS 负责安全通道。
  2. 数字签名不是“私钥加密、公钥解密”。
  3. ECDHE 和证书身份密钥解决不同问题。
  4. Server 通常发送 Leaf + Intermediate，Root 通常来自本地 Trust Store。
  5. CertificateVerify 与 Finished 作用不同。
