Chapter 05 · Secure HTTP

HTTP / HTTPS / TLS：
怎样同时解决“业务语义、机密性、完整性和身份认证”？

先把三层职责分开：HTTP 定义业务语义，TLS 负责身份认证、机密性与完整性，TCP 负责可靠有序搬运 TLS 字节。真正理解 HTTPS 的关键，是弄清“哪把钥匙干什么、谁在证明谁”。

最容易混的两组东西

  • ECDHE ephemeral key ≠ Certificate identity key。
  • Certificate Signature ≠ CertificateVerify ≠ Finished。

必须分开的两条时间线

  • 网站部署前：CA 签发 Certificate。
  • 用户访问时：Browser 与 Server 完成 TLS 1.3 Handshake。

业务语义

1. HTTP Message 与 Framing：Request / Response 是怎么被表达出来的？

Request
GET /products?lang=zh-CN HTTP/1.1 Host: shop.example.com Accept: text/html Cookie: session_id=abc123 [optional body]

Request 由 Start Line、Headers、空行和可选 Body 组成。

Response
HTTP/1.1 200 OK Content-Type: text/html Content-Length: 12580 Cache-Control: max-age=60 ...

Response 由 Status Line、Headers、空行和可选 Body 组成。

Content-Length

明确告诉接收方 Body 有多少字节，是 HTTP/1.1 常见消息边界方式之一。

Chunked

HTTP/1.1 可用 Transfer-Encoding: chunked 流式发送未知总长度的 Body。

HTTP/2+

HTTP/2/3 使用自己的 Frame，不再靠 HTTP/1.1 文本分隔方式表达消息边界。

i
GET / POST 的核心区别不是“参数放 URL 还是 Body”
HTTP Method 主要表达操作语义。Safe、Idempotent 等性质要按协议语义理解，而不是按表单习惯死记。
同一个域名会出现在不同协议阶段

2. DNS hostname、TLS SNI、HTTP Host / :authority 不是一个字段

阶段字段 / 概念作用
DNShostname把名称解析成 A / AAAA 等地址候选。
TLSSNI共享 IP:443 时，帮助 Server 选择站点配置和证书。
HTTP/1.1Host选择 Virtual Host / Route。
HTTP/2 / 3:authority承担目标 authority / host 语义。
URL: https://shop.example.com/products DNS hostname: shop.example.com TLS SNI: shop.example.com Certificate SAN: shop.example.com HTTP Host / :authority: shop.example.com
!
值常常一样，但职责不同
DNS 为寻址，SNI 为 TLS 虚拟主机选择，Host / :authority 为 HTTP 目标站点和路由选择。
HTTP 状态与缓存

3. Cookie、Session、Cache：无状态 HTTP 为什么还能“记住你”？

Cookie
Set-Cookie: session_id=abc123; Secure; HttpOnly; SameSite=Lax

Browser 按规则保存，并在匹配请求中自动携带。

Session
Cookie session_id ↓ Server Session Store ↓ user_id / cart / roles

Session 是 Server 侧会话状态模型，Cookie 只是客户端携带标识或状态的一种方式。

Cache
Cache-Control: max-age=60 ETag: "v42" If-None-Match: "v42" ↓ 304 Not Modified

Freshness 与 Validation 让客户端避免不必要的完整下载。

i
Secure / HttpOnly / SameSite 解决不同问题
Secure 约束安全传输，HttpOnly 限制普通前端 JS 读取，SameSite 控制跨站请求中的 Cookie 携带策略。
密码学最小模型

4. Symmetric、Public-key、Hash、Digital Signature：四种能力先分开

Symmetric

高效保护大量数据

例如 AES-GCM、ChaCha20-Poly1305，适合 TLS Application Data。

Public-key

Public / Private Key

用于身份签名、密钥建立等场景；不适合直接加密全部 HTTPS 流量。

Hash

单向摘要

用于完整性、签名、KDF 等；Hash 不是 Encryption，没有“解密 Hash”。

Signature

Private Key 签，Public Key 验

不要把数字签名理解成“私钥加密、公钥解密”。

i
AEAD 为什么重要？
现代 TLS 需要同时提供 Encryption 与 Integrity。AEAD（如 AES-GCM）把机密性与认证标签结合起来，避免只加密却无法可靠检测篡改。
两类公钥

5. TLS 里最容易混的东西：ECDHE Key Share ≠ Certificate Identity Key

ECDHE Ephemeral Key Share
Client ephemeral key pair + Server ephemeral key pair ↓ ECDHE ↓ Shared Secret ↓ HKDF ↓ Handshake / Application Keys

解决：本次连接怎样建立共享秘密，并提供 Forward Secrecy（前向保密）。

Certificate Identity Key
Server Identity Private Key ↓ sign current handshake transcript ↓ CertificateVerify Certificate Public Key ↓ verify signature

解决：当前握手方是否真的持有这个 Certificate 对应的身份 Private Key。

!
一句话
ECDHE 负责“怎么安全得到本次连接的密钥”，Certificate Key 负责“你到底是谁”。
证书信任

6. CA / Certificate Chain：为什么 Browser 会相信这个 Server？

时间线 A · 网站部署前
Site / Operator ↓ CSR + Domain Control CA / Intermediate CA ↓ verify Signed Leaf Certificate ↓ Deploy: Private Key Leaf Certificate Intermediate Certificate(s)

Server Private Key 通常由站点一侧生成和保管；CA 负责验证并签发证书。

时间线 B · 用户访问时
Server sends: Leaf Certificate Intermediate Certificate(s) Browser / OS already has: Trusted Root CA in local Trust Store

运行时 Browser 本地验证 Certificate Chain，并不是每次访问都向 CA “实时请示是否批准”。

Leaf / Server Certificate
↓ signed by
Intermediate CA
↓ chains to
Trusted Root CA
↓ configured trust anchor
Browser / OS Trust Store
i
Root 自签名 ≠ 因为“自己签自己”所以可信
Root 真正的信任来源，是它被 Browser / OS 配置成 Trust Anchor。

三种“验证”

8. Certificate Signature、CertificateVerify、Finished 到底各证明什么？

机制谁产生主要证明
Certificate SignatureCA / Intermediate CACA 对 Certificate 中的身份与 Public Key 做签发背书。
CertificateVerify当前 TLS Server当前握手方掌握 Leaf Certificate 对应 Private Key，并把身份绑定到当前 Handshake Transcript。
Finished双方各自产生双方已经拥有正确 Handshake Secret，并对握手 transcript 理解一致，没有被悄悄改写。
i
三者不是“重复签名”
一个是 CA 对证书做背书，一个是 Server 对本次握手证明私钥持有权，一个是双方确认握手秘密与 transcript 一致。
握手优化

9. Session Resumption / PSK / 0-RTT：第二次连接为什么可以更快？

Resumption / PSK
Full Handshake ↓ derive resumption state / PSK ↓ Next Connection ↓ ClientHello carries PSK identity / binder ↓ Server accepts ↓ shorter handshake

目标是减少往返与重复认证成本。TLS 1.3 恢复可以使用 PSK，也可与新的 (EC)DHE 组合。

0-RTT Early Data
ClientHello + Early Application Data ↓ Server may process data before new handshake fully completes

低延迟的代价是 Replay Risk。不可安全重放的操作不能随便放进 0-RTT。

版本与证书状态

10. TLS 1.2 vs 1.3，以及 OCSP / CRL 在哪里出现？

TLS 1.2 → TLS 1.3

TLS 1.3 简化了主握手、移除了许多旧算法与组合，并把更多握手内容更早放进加密保护之下。不要把 TLS 1.2 的消息序列直接套到 TLS 1.3。

Revocation Status

CA 不是每次 TLS 都实时批准连接，但证书状态仍可能通过 CRL、OCSP、OCSP Stapling 或 Browser/平台自己的机制参与“是否已撤销”的判断。

CRL

CA 发布 Certificate Revocation List，Client 获取后检查证书序列号是否已撤销。

OCSP

查询证书状态的协议之一，但实际 Browser 策略并不完全统一。

OCSP Stapling

Server 可把较新的 OCSP 状态证明随握手提供，减少 Client 直接查询 OCSP Responder 的需要。

安全边界

11. HTTPS 能保护什么，又不能保护什么？

TLS 通常保护

HTTP Method、Path、Headers、Cookie、Authorization、Body、Response Body 等应用内容。

仍可能暴露 / 被推断

IP、packet size、timing、TCP/UDP metadata；经典 SNI 与传统 DNS 也可能暴露 hostname。ECH 试图进一步保护 ClientHello 中的敏感部分，但部署支持取决于实际环境。

TLS Authentication

回答：我连到的 Server 是否持有目标 hostname 对应可信 Certificate 的 Private Key？

Application Authentication

回答：当前用户是谁？通常由 Session、Cookie、Bearer Token、OAuth 等解决。

HTTPS 不解决

SQL Injection、XSS、Broken Access Control、弱密码、Server 被入侵等应用安全问题。

12. 一页总结：HTTPS 是多种机制协作，不是一把“万能钥匙”

HTTP → 业务语义 TLS → Certificate Chain → CertificateVerify → (EC)DHE / PSK → HKDF → Finished → AEAD Traffic Keys TCP → 可靠有序 Byte Stream 最关键： ECDHE Ephemeral Key ≠ Certificate Identity Key Certificate Signature ≠ CertificateVerify ≠ Finished CA 签发时间线 ≠ 用户运行时 TLS 握手时间线
