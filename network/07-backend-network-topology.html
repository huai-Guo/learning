Chapter 07 · Production Topology

真实后端网络拓扑：
一次公网请求怎样真正进入业务服务？

真实系统不是“Browser 直接连业务进程”。更常见的是先进入 CDN / Edge / WAF / LB / Gateway 等入口层，再通过 Service Discovery + RPC 进入内部服务，最后访问 Redis / MySQL 等基础设施。

这章最重要的纠错

  • CDN → WAF → LB → TLS → Gateway 不是唯一固定顺序。
  • TLS Termination 是某个节点的能力，不是一台必然独立存在的“设备”。

思维升级

  • 一次业务 Request 可以跨很多独立 TCP / QUIC 连接。
  • 角色图、协议图、身份图必须分开。

2. 三种典型入口拓扑：TLS 到底在哪里结束？

A · Edge Termination

边缘解 TLS，再回源

Client ↓ TLS CDN / Edge ├─ TLS Termination ├─ WAF ├─ Cache └─ L7 Routing ↓ HTTP or TLS Origin / Gateway ↓ Backend

适合 Edge 需要读取 HTTP 内容做缓存、WAF、路由的场景。

B · L4 Passthrough

入口只做连接转发

Client ↓ TLS L4 Load Balancer ↓ TLS passthrough Nginx / Envoy / Backend ├─ TLS Termination └─ HTTP Routing

L4 LB 不需要看到 HTTP 内容，证书和 Private Key 可以留在后面的 TLS Endpoint。

C · Re-encrypt

边缘解密后，内部再次 TLS

Client ↓ TLS Session A Edge / Gateway ├─ WAF / Auth / Routing └─ TLS client ↓ TLS Session B Backend

中间层能治理应用请求，同时内部链路继续加密。

i
因此不要把 TLS Termination 画成固定夹在 “LB 后、Gateway 前” 的独立设备
它应该标注在“哪一个节点结束了这段 TLS Session”上。
公网入口

3. DNS、CDN、WAF、L4/L7 LB 分别负责什么？

DNS
api.example.com ↓ 203.0.113.50 这个 IP 可能属于： CDN Edge / Anycast / WAF / Public LB 而不是最终业务实例

DNS 通常选择“先进入哪个入口”，后面的 LB / Discovery 还会继续选择实际后端。

CDN
User ↓ Nearby Edge ├─ Cache Hit → 直接返回 └─ Cache Miss → 回源 Origin

所以用户请求量与 Origin 实际 QPS 可以完全不同。

WAF

观察 HTTP Method、Path、Header、Cookie、Body、频率与攻击模式；更偏 L7。

L4 LB

更偏 IP / Port / Transport / Connection 级分发，可采用 NAT、Proxy、DSR 等不同实现。

L7 LB

解析 HTTP 等应用协议，可按 Host / Path / Header / Cookie 做 Request-level Routing。

入口软件栈

4. Nginx、Envoy、API Gateway：能力重叠，但关注点不同

Nginx

Reverse Proxy、TLS Termination、Static File、HTTP Routing、Load Balancing、Cache 等都很常见。

Envoy

现代 L7 Proxy、HTTP/2 / gRPC、Dynamic Discovery、Retry / Timeout、mTLS、Telemetry、Service Mesh Data Plane。

API Gateway

更强调 External API 入口：Auth、Quota、Rate Limit、Routing、API Policy、Protocol Translation、Tenant。

Reverse Proxy
Client ↓ Reverse Proxy ↓ Backend

代表 Server 一侧，Client 通常不知道最终 Backend。

Forward Proxy
Client ↓ Forward Proxy ↓ Internet Server

更像代表 Client 出网。

5. Proxy 之后，Backend 为什么经常看不到真实 Client TCP Peer？

Client 1.2.3.4 ↓ Proxy 10.0.0.5 ↓ new TCP connection Backend 10.0.0.20 Backend TCP Peer = 10.0.0.5

因为 Backend 这一段连接的真实 TCP 对端就是 Proxy。

传递 Original Client 元数据
HTTP: Forwarded X-Forwarded-For X-Forwarded-Proto X-Forwarded-Host L4: PROXY Protocol

HTTP Header 与通用连接级元数据属于不同层。

!
必须建立 Trusted Proxy Boundary
Client 可以自己伪造 X-Forwarded-For。可信 Edge 应清理/覆盖不可信头，再按确定规则追加地址；Backend 只信任明确的 Proxy 链。
进入内部服务网络

6. Gateway → Service Discovery → Load Balancing → RPC

协议切换
Browser → Gateway HTTP/2 + JSON Gateway → Order Service gRPC + Protobuf

Gateway 可以完成 Auth、Rate Limit、Routing、Aggregation 与 Protocol Translation。

服务寻址
inventory-service ↓ Discovery 10.20.1.7:9000 10.20.1.8:9000 10.20.2.3:9000 ↓ Load Balancing Pick 10.20.1.8 ↓ Connect / Reuse ↓ RPC

Discovery 回答“有哪些实例”；Load Balancing 回答“这一次选哪个实例”。

Client-side LB

调用方直接获取 Endpoint Set，并自己选择目标。

Server-side LB

调用方只连接稳定 VIP / Proxy，由中间层选择后端。

Sidecar / Mesh

业务进程把 Discovery、LB、mTLS、Telemetry 等能力委托给本地 Sidecar。

一个业务请求会“裂变”

7. 一次业务 Request，往往不是一条端到端 TCP Connection

Browser → CDN Connection A CDN → Gateway Connection B Gateway → Feed Service Connection C Feed → User Service Connection D Feed → Recommend Service Connection E Feed → Redis Connection F Feed → MySQL Connection G
i
这解释了为什么不同层看到的 “peer” 不一样
每个代理 / 服务边界都可能结束上一条连接并建立下一条连接。一次业务调用链和一条 TCP Connection 是两个不同概念。
连接与时延

8. Connection Pool、Deadline Budget、Retry Storm

Connection Pool
Service A ├─ Conn A → Service B1 ├─ Conn B → Service B2 └─ Conn C → Service B3

每次都重新 connect / TLS / close 成本太高，长期连接与 Pool 是常见工程手段。

Deadline Budget
User 1000ms ↓ Gateway 900ms ↓ Service A 700ms ↓ Service B 500ms ↓ DB 300ms

下游预算小于上游预算，上游才有时间做错误处理与清理。

Retry Storm（重试风暴）

系统变慢 → Timeout 增多 → 各层重试 → 流量放大 → 更慢。Retry 必须配合 Backoff、Jitter、Retry Budget 与 Idempotency。

Circuit Breaker / Load Shedding

持续失败时快速失败或降级；容量不足时主动拒绝部分请求，保护剩余系统。

数据层也是网络

9. Redis / MySQL：别把数据库访问想成本地函数调用

真实路径
Application ↓ DB / Redis Driver ↓ Socket ↓ TCP ↓ IP ↓ Private Network ↓ Redis / MySQL Server

因此故障除了 SQL，还可能来自 Connect Timeout、Read Timeout、Pool Exhaustion、Reset、DNS、Route 与 Packet Loss。

Pool 也会出故障
Queries become slower ↓ Connections occupied longer ↓ Pool Exhausted ↓ Wait / Timeout

根因可能是 SQL、Pool Size、Connection Leak、下游抖动或上游并发突然升高。

运行与治理

10. Health Check、Readiness、Liveness、Drain、mTLS、Service Mesh

Liveness

进程是否坏到应该重启。

Readiness

当前是否应该接收新流量。可以 Alive but Not Ready。

Connection Draining

停止新请求，等待 in-flight 请求完成后再下线实例。

mTLS

Service-to-Service 双向身份、加密与完整性保护。

API Gateway · North-South

更偏外部 Client → 内部系统：Auth、Rate Limit、API Policy、Routing。

Service Mesh · East-West

更偏 Service ↔ Service：mTLS、Discovery、Retry、Timeout、Traffic Policy、Telemetry。

分层排障

12. 遇到“访问超时”，不要直接跳到数据库

统一排障链
DNS ↓ Edge / CDN ↓ TCP / QUIC ↓ TLS ↓ WAF / LB ↓ Gateway ↓ Backend ↓ RPC Dependency ↓ Redis / DB

逐段问：有没有到？有没有建连？有没有握手？有没有被拒？有没有排队？有没有超时？有没有重试？

两个典型误判
IP + port 能通 ≠ hostname 完整链路一定正常 ping 能通 ≠ TCP 443 / TLS / HTTP 一定正常

域名链路还涉及 DNS、IPv4/IPv6、SNI、Certificate、Host/:authority、WAF 与 Gateway Routing。

状态码典型含义常见排查方向
502Gateway 没拿到有效 Upstream 响应Reset、Protocol Error、Invalid Response
503Service UnavailableNo Healthy Backend、Overload、Circuit Open、Load Shedding
504Gateway 等 Upstream 超时上游慢、排队、依赖阻塞、Deadline 不合理

13. 全课程收束：真实生产网络的核心不是“协议多”，而是“边界多”

Client ↓ Internet Public Edge / Entry ├─ CDN / Cache ├─ WAF ├─ L4/L7 LB └─ TLS Termination or Passthrough ↓ Gateway / Proxy ├─ Auth ├─ Rate Limit ├─ Routing └─ Protocol Translation ↓ Backend Services ├─ Discovery ├─ Load Balancing ├─ RPC └─ mTLS ↓ Redis / MySQL / MQ 同时记住： 一次业务 Request ≠ 一条端到端 TCP Connection 角色图 ≠ 协议图 ≠ 身份图
