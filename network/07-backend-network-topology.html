Chapter 07 · Production Topology

真实后端网络拓扑：
一次公网请求怎样真正进入业务服务？

真实系统通常不是 Browser 直接连业务进程，而是先进入 DNS / CDN / Edge / WAF / LB / Gateway，再通过 Service Discovery + RPC 进入内部服务，最后访问 Redis / MySQL 等基础设施。

先记一句话

  • 这是一张“职责图”，不是“必须有很多台机器”的设备清单。
  • 一个 Edge 节点完全可能同时承担 TLS、WAF、Cache、L7 Routing 等职责。

最重要的思维升级

  • 一次业务 Request 往往跨越多条独立连接。
  • 角色图、协议图、身份图必须分开理解。

公网入口

1. DNS / CDN / WAF / LB：用户首先连到的通常不是业务 Server

api.example.com ↓ DNS 203.0.113.50 ↓ CDN / Anycast / WAF / Public LB ↓ 10.23.4.17 10.23.4.18 10.23.5.22 ↓ Backend Instances
CDN

Cache Hit 时直接在 Edge 返回；Cache Miss 才回源 Origin。它不只是“缓存服务器”，还可能承担 TLS、DDoS、WAF 等职责。

L4 LB

主要按 IP / Port / Transport / Connection 分发，不必理解完整 HTTP Request。

L7 LB

可以按 Host / Path / Header / Cookie 等做 Request-level Routing。

i
WAF 与 Network Firewall 不同
Firewall 更偏 IP / Port / Protocol / Connection State；WAF 更偏 HTTP Method / Path / Header / Cookie / Body / Request Pattern。
TLS 在哪里结束

2. Termination、Re-encrypt、Passthrough：LB 不一定解 TLS

Terminate
Client → TLS → Edge → HTTP → Backend

Edge 拿到 HTTP 明文，适合做 L7 Routing。

Re-encrypt
Client → TLS A → Edge → TLS B → Backend

Edge 能治理请求，同时内部链路继续加密。

Passthrough
Client → TLS → L4 LB → Backend

中间 LB 不解 TLS，也就不能按 Path/Header 做完整 L7 判断。

!
为什么 L7 Routing 经常要求先解 TLS？
因为 Host、Path、Header 等 HTTP 内容本来就在 TLS 里面。想看请求内容，就得先结束或解密这层 TLS。
代理与原始客户端信息

3. Reverse Proxy 之后，Backend 为什么经常看不到真实 Client IP？

Client 1.2.3.4 ↓ Proxy 10.0.0.5 ↓ new TCP connection Backend 10.0.0.20 Backend TCP Peer = 10.0.0.5

如果 Proxy 重建了 TCP Connection，后端看到 Proxy 是完全正常的。

如何传递 Original Client 信息
HTTP: X-Forwarded-For X-Forwarded-Proto X-Forwarded-Host Forwarded L4: PROXY Protocol

X-Forwarded-* 属于 HTTP 层；PROXY Protocol 适合更通用的连接级代理。

!
必须建立 Trusted Proxy Boundary
Client 自己也能伪造 X-Forwarded-For。Edge / Gateway 需要清洗不可信头并按明确策略追加真实信息，Backend 只信任已知 Proxy。
从公网协议进入内部 RPC

4. Gateway → Service Discovery → Load Balancing → RPC

协议可以切换
Browser → Gateway HTTP/2 + JSON Gateway → Order Service gRPC + Protobuf

Gateway 既可以做 Auth / Rate Limit / Routing，也可以做 Protocol Translation。

服务寻址
inventory-service ↓ Discovery 10.20.1.7:9000 10.20.1.8:9000 10.20.2.3:9000 ↓ Load Balancing Pick 10.20.1.8 ↓ RPC

Discovery 回答“有哪些实例”；Load Balancing 回答“这次选哪个”。

连接与时延

5. Connection Pool、Deadline Budget、Retry Storm

Connection Pool
Service A ├─ Conn A → Service B1 ├─ Conn B → Service B2 └─ Conn C → Service B3

每次都 socket/connect/TLS/close 成本太高，因此服务间通常复用长期连接。

Deadline Budget
User 1000ms ↓ Gateway 900ms ↓ Service A 700ms ↓ Service B 500ms ↓ DB 300ms

下游预算比上游短，才能让上游留出失败处理和清理时间。

Retry Storm

系统变慢 → Timeout 增多 → 各层重试 → 流量放大 → 系统更慢。Retry 必须配合 Backoff、Jitter、Budget、幂等、熔断和 Load Shedding。

连接生命周期

Keepalive、Idle Timeout、Max Connection Age、Drain 分别解决不同问题。Connection closed by peer 不一定意味着网络坏了。

数据层也是网络

6. Redis / MySQL：别把数据库访问想成本地函数调用

真实路径
Application ↓ DB / Redis Driver ↓ Socket ↓ TCP ↓ IP ↓ Private Network ↓ Redis / MySQL Server

所以数据库故障除了 SQL，还可能来自 connect/read timeout、Pool Exhaustion、reset、DNS、route 和 packet loss。

连接池也会成为瓶颈
Pool Size fixed ↓ Queries become slower ↓ Connections occupied longer ↓ Pool Exhausted ↓ Wait / Timeout

表面上像“数据库突然慢”，根因可能是 SQL、Pool Size、Connection Leak 或上游并发变化。

运行治理

7. Readiness、Liveness、Draining、mTLS、Service Mesh

Liveness

进程是否坏到应该重启。

Readiness

当前是否应该接新流量。可以 Alive but Not Ready。

Connection Draining

停止接新请求，等待 in-flight 请求完成后再下线。

mTLS / Mesh

Service-to-Service 双向身份、加密与流量治理。

API Gateway

更偏 North-South：外部 Client → 内部系统。常做 Auth、Rate Limit、API Policy。

Service Mesh

更偏 East-West：Service ↔ Service。常做 mTLS、Discovery、Retry、Timeout、Telemetry。

三张图必须分开

8. 角色图、协议图、身份图分别回答不同问题

角色图
Browser ↓ Edge ↓ LB / Gateway ↓ Backend ↓ Redis / MySQL

回答：谁在做事？

协议图
Browser → Edge HTTP/2+TLS+TCP or HTTP/3+QUIC+UDP Gateway → Backend gRPC / HTTP / Thrift

回答：每一段跑什么协议？

身份图
DNS Name TLS Identity TCP Peer Original Client IP Application User Service Identity Trace ID

回答：“你是谁”在每一层分别怎么定义？

∞
Trace ID ≠ TCP Connection ≠ QUIC Connection ID
一次 Trace 可以跨多个服务、多个请求和多条底层连接。
分层排障

9. 遇到“访问超时”，不要直接跳数据库

统一排障链
DNS ↓ CDN / Edge ↓ TCP / QUIC ↓ TLS ↓ WAF ↓ LB ↓ Gateway ↓ Backend ↓ RPC ↓ Redis / DB

逐段问：有没有到？有没有建连？有没有握手？有没有被拒？有没有排队？有没有超时？有没有重试？

两个典型误判
IP + port 能通 ≠ hostname 完整链路一定正常 ping 能通 ≠ TCP 443 / TLS / HTTP 一定正常

域名链路还涉及 DNS、IPv4/IPv6、SNI、Certificate、Host / :authority、WAF 和 Gateway Routing。

状态码典型含义常见排查方向
502Gateway 没拿到有效 Upstream 响应Reset、Protocol Error、Invalid Response
503Service UnavailableNo Healthy Backend、Overload、Circuit Open、Load Shedding
504Gateway 等 Upstream 超时上游慢、排队、依赖阻塞、Deadline 不合理

10. 一页总结：真实生产网络的核心不是“协议多”，而是“边界多”

Browser ↓ DNS CDN / Edge ↓ WAF ↓ L4 / L7 LB ↓ TLS Termination / Passthrough ↓ Nginx / Envoy / API Gateway ↓ Backend Service ↓ Service Discovery ↓ Load Balancing ↓ RPC ↓ Redis / MySQL / MQ 同时记住： 一次业务 Request ≠ 一条端到端 TCP Connection 角色图 ≠ 协议图 ≠ 身份图

最该记住的 6 句话

  1. DNS IP 常是入口，而不是最终业务实例。
  2. L4 按连接，L7 按请求。
  3. TLS 终止点决定谁能看到 HTTP 内容。
  4. Proxy 后 Backend 的 TCP Peer 常不是原始 Client。
  5. Discovery 与 Load Balancing 是两个步骤。
  6. 数据库访问仍然是网络 I/O。
